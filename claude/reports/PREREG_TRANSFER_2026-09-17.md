# Pre-registration — T1: does retrieving the system's own verified past work help on a new task?

**Written 17 September 2026. Committed BEFORE any arm is run.**
Sources: Kimi Round 50 (T1), Kimi Round 51 (compositional hold-outs, decomposition,
acceptance thresholds).

**A pass on synthetic tasks demonstrates the mechanism only.**

That sentence is required to appear in the final report verbatim, and it is the honest
ceiling on everything below. These tasks are generated by a grammar this repo wrote.
Showing that retrieval helps here shows that the retrieval mechanism can help — it does
not show that the system's real memory of its real work helps on real questions. That
is a later, harder experiment, and this one is the precondition for bothering with it.

---

## 1. The question, and why it is worth running

The system stores a great deal about its own past work: `memory/brain_journal.jsonl`
(2.1 MB), cycle reviews, a statements index, a prophecy ledger. Almost nothing reads any
of it for RELEVANCE. `core/brain.py:313 _memory()` returns the five most RECENT
same-kind verdicts — recency, not relevance. `core/embed_index.search` is the only
relevance retrieval in the repo, and until 17 Sep it had no index to search.

If retrieval of past verified work does not improve performance on a new task, the
knowledge layer has no consumer and building more of it is building a warehouse nobody
collects from. That is the decision this experiment informs.

**A concrete instance of the same gap, found during STEP 0 and recorded, not fixed:**
`canon_invariants.json` is `{"invariants": []}` after months. Not because nothing was
learned — the last six nightly reviews carry the same lesson in six paraphrases —
but because `brain.lesson_key()` compares model prose by exact string equality, so
three *consecutive identical strings* are required and never occur. Left untouched
until after T1, by instruction.

## 2. Task family

`tools/transfer_tasks.py`, committed at `f6c8195`, `METHOD_VERSION = transfer_tasks/2`.

Six **primitives**: `linear_trend`, `mean_reverting`, `alternating`, `accelerating`,
`level_shift`, `damped_oscillation`. A task's latent structure is one primitive or a
**composition** of two. Each task shows 8 values and asks about the 9th.

| set | contents | n |
|---|---|---:|
| memory episodes | all six singles (6 each) + five named compositions (4 each) | **56** |
| test: `single` | a primitive memory has seen alone | 24 |
| test: `seen_composition` | a composition memory contains | 24 |
| test: **`holdout_composition`** | a composition **absent from memory**, from primitives it has | **16** |
| **test total** | | **64** |

**Frozen task-set sha256: `cd574b575f855c055e1ea473a46aae654bbfab58f31d5417d365cc8a2bd660fa`**
(`tools/transfer_tasks.py --ledger`; covers episodes and tests together).

The ten hold-out compositions: `linear_trend+accelerating`, `linear_trend+level_shift`,
`mean_reverting+alternating`, `mean_reverting+accelerating`,
`mean_reverting+damped_oscillation`, `alternating+level_shift`,
`alternating+damped_oscillation`, `accelerating+level_shift`,
`accelerating+damped_oscillation`, `level_shift+damped_oscillation`.

**Why hold-outs.** If memory and test shared whole regimes, a pass would show
RECOGNITION — "I have met this exact kind of series before" — and be reported as
transfer. Answering a hold-out by retrieval requires carrying something from the parts
to a whole never seen.

**Leak audit** (`answer_leak_audit`, asserted in `--selftest`, fails loud):

- **tail 3-gram in memory: 0.** A test's own last three values appearing as a
  contiguous run inside an episode would hand over the continuation. This is the leak,
  and it is the hard failure.
- bare answer-value coincidence: 4 of 64 tests (rate 0.0625) against 504 memory values.
  Float equality at 2dp in a bounded range collides by the birthday argument; an episode
  containing 47.3 somewhere tells a retriever nothing about a test whose answer is 47.3.
  Reported, not treated as a leak. Threshold for implausibility: rate > 0.10.

**The latent label never enters a prompt, an episode, or the retrieval key.** The
retrieval key is the series and its step differences, nothing else.

## 3. The question asked of the model

Each task asks for the **direction** of the next step (UP or DOWN) and a **probability**
`p` that it is UP. One question yields both metrics. A "predict the next value" question
was rejected: scoring it needs a tolerance, and a tolerance is a free parameter that
could be chosen after seeing results.

## 4. Model and decoding — frozen, identical in every arm

| setting | value | why |
|---|---|---|

Measured 17 Sep: at `num_predict=64` the entire budget goes to reasoning and **content comes back empty** — every trial would score as an unparseable failure and the experiment would measure the token budget, not memory. `think=False` also runs **7.7× faster** (3.0 s vs 23.2 s). |
| temperature | 0.0 | |
| `num_predict` | 128 | |
| prompt skeleton | identical across arms; only the memory block differs | |
| latency | 3.0 s/call measured (8.9 s median with thinking on, 22.4 s first call) | 64 tasks × 3 arms = 192 calls ≈ 10 min. **n is not budget-bound.** |

## 5. Arms — three, paired, every task run under all three

| arm | memory block |
|---|---|
| **memory-on** | top-k episodes from `core/embed_index.search` over the episode index |
| **memory-off** | **matched-length filler** — same block length, no episode content |
| **shuffled** | equal token count, episodes drawn from **non-matching** tasks (no shared primitive), **order counterbalanced** |

Memory-off uses filler rather than an empty block so that any difference between on and
off cannot be an artefact of prompt length. Shuffled holds length *and* episode-shaped
content constant, so the difference between on and shuffled is what retrieval
specifically bought.

## 6. Metrics and decomposition

- **success rate** — direction correct.
- **Brier** — `(p - actual_up)²`, mean. Reported as Brier, computed as a mean squared
  error. (See `claude/reports/SCOREBOARD_LABEL_AUDIT_2026-09-17.md` for why this
  sentence is written explicitly.)
- **paired bootstrap**, 10,000 resamples over tasks, 95% CI on the paired difference.

**Decomposition, reported as three numbers:**

```
total               = on  −  off
retrieval-specific  = on  −  shuffled
format              = total − retrieval-specific   (i.e. shuffled − off)
```

The third is the part explained by having episode-shaped text at all, rather than by
those particular episodes.

## 7. Acceptance thresholds — declared now

A **PASS** requires all three:

1. **on − off ≥ 15 percentage points** on success rate, with the paired bootstrap 95% CI
   excluding 0.
2. **on − shuffled ≥ 7.5 pp** (half the margin), CI excluding 0.
3. **Benefit correlates with LATENT similarity**: Spearman ρ of per-task benefit
   (on − off) against latent-structural similarity to the retrieved episode is positive
   with CI excluding 0, **and exceeds** the same correlation against surface (token)
   similarity.

Condition 3 is what separates transfer from lookup. Measured already at the retrieval
layer: mean latent similarity of the top hit is 0.55 against mean surface similarity
0.08, so the two are distinguishable on this task set.

**Hold-outs are reported separately**, with their own success rates, CI and n=16. A
result that passes overall and fails on hold-outs is reported as exactly that.

Anything short of all three is a **FAIL**, and the report says FAIL. A null result will
not be softened, re-cut, or described as "promising".

## 8. Failure paths, named before the run

| event | treatment |
|---|---|
| model reply not parseable | **FAILURE of that trial.** Never dropped, never retried. Counted and reported per arm. |
| parse-failure rate differs materially between arms | the Brier comparison is **VOID** — the arms are no longer the same sample. Success rate still stands, since unparseable counts as failure. |
| an arm errors (transport, model unavailable) | **reported, never imputed.** No arm is filled in from another. |
| embedder falls back to hashed vectors | the run is **void**, not corrected. A hashed vector is a placeholder for meaning; `tools/retrieval_at_k.py` refuses to score across two spaces for the same reason. |
| generation cannot produce a task | already refused at generation time by the flat-step floor; a coin-flip task never enters the set. |

**If the run is too slow, the tasks get simpler — never fewer.** n ≥ 64 with ≥ 16
hold-outs is fixed here and is not a budget variable.

## 9. What each outcome will be taken to mean

| outcome | reading |
|---|---|
| all three conditions pass, hold-outs included | The retrieval mechanism transfers on this grammar. **Mechanism only.** Justifies building the real-memory version and testing it on real work. |
| passes overall, fails on hold-outs | Recognition, not transfer. The layer helps when the whole shape was seen before and not otherwise — a much weaker and much more limited consumer. |
| on beats off but not shuffled | The gain is **format**, not retrieval. Episode-shaped text in the prompt helps; *those* episodes do not. The knowledge layer is not what is paying. |
| benefit tracks surface similarity, not latent | Lookup by resemblance. Would not survive a domain where the surface changes. |
| no arm separates | On this grammar, retrieved past work does not help. Reported as a null. It does not prove the real memory layer is useless — it does remove the main reason to assume it is useful. |

# ADDENDUM — 17 September 2026, embedder selection

**Appended after the text above was frozen and committed (`0061c68`). Nothing above is
edited.** Written BEFORE any T1 arm has run, so the choice below is made on retrieval
numbers alone and cannot be tuning on the outcome.

## The rule, as instructed

- The memory arm uses the embedder with the higher **hold-out recall@1** (n = 16).
- A tie, or a difference under **0.0625** (one task of sixteen), keeps the current
  embedder — no change without evidence.
- The void rule stands: a fallback to hashed vectors voids the run.
- The stored statement shards are not re-embedded, whichever model wins.

## Result table A — current embedder

`qwen2.5:3b` (generative, dim 2048), 56 episodes / 64 tests, ledger
`cd574b575f855c055e1ea473a46aae654bbfab58f31d5417d365cc8a2bd660fa`:

| metric | value | chance |
|---|---:|---:|
| recall@1 | **0.7344** | 0.2969 |
| recall@5 | 1.0 | 0.8594 |
| **hold-out recall@1 (n=16)** | **0.625** | — |
| hold-out recall@5 | 1.0 | — |

Diagnosed rather than assumed. From this repo's Python, in the same shell, at the same

404  https://registry.ollama.ai/v2/          <- reachable; 404 is the bare-path answer

So the network is not blocked and the registry is not down. The **ollama server process**
is being denied outbound access — a host firewall rule on the ollama binary. That is not
something this session can change, and no amount of retrying will move it.

## Decision

**The memory arm uses `qwen2.5:3b`**, by the rule's own second clause: a difference under
0.0625 keeps the current embedder, and an *unmeasurable* alternative provides less
evidence than a small difference does. Substituting a model that cannot be loaded, or
guessing at its numbers, would be worse than proceeding with a measured one.

This is a limitation of the result, not a fix for one. It goes in the report as such:
the memory arm was retrieved by a generative model pressed into embedding duty, at a
measured hold-out recall@1 of 0.625, and the comparison against a purpose-built embedder
is **outstanding, not declined**.

To close it, one command, run where the ollama daemon is permitted outbound — in this
session the `!` prefix runs it in the user's own shell:

```
ollama pull nomic-embed-text
venv\Scripts\python.exe tools/retrieval_at_k.py --run --model nomic-embed-text
```

If that number beats 0.625 by at least 0.0625, the rule requires re-running T1 with it,
and this addendum is the pre-registration of that re-run.
